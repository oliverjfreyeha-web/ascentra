# Database

Postgres on Supabase. The app reaches it only through the API (`lib/db`, service role). Row-level
security is on for every table and denies by default.

## Files

| Path | What it is |
| --- | --- |
| `migrations/0001_accounts.sql` … `0004_row_level_security.sql` | The migrations, applied in order. Each one records itself in `private.schema_migrations` and refuses to run twice. |
| `apply/F3.sql` | The one file to paste for F3: 0002 → 0004 in a single transaction. Generated by `npm run db:bundle`; CI fails if it is stale. |
| `apply/F4.sql` | The one file to paste for F4: 0005 (admin invites, Owner protections). Requires F3. |
| `apply/F5.sql` | The one file to paste for F5: 0006 (audit chain and its verifier). Requires F4. |
| `apply/F6.sql` | **The one file to paste for F6**: 0007 (trusted devices, sessions, sharing tracker, steps, appeals). Requires F5. |
| `apply/B1.sql` | **The one file to paste for B1**: 0008 (billing: Stripe lifecycle, customers, events, Automatic Renewal Terms v0.1). Requires F6. |
| `ops/create-test-learner.sql` | Owner-only, by hand: one adult test learner for an existing Clerk user (see below). Not a migration. |
| `verify.sql` | Run after applying. First row is the verdict. |
| `test/supabase-shim.sql` | Tests only: recreates Supabase's API roles and `auth.jwt()` on plain Postgres. Never apply it to Supabase. |

## A test learner (Owner only, until sign-up opens in B2)

Sign-up is closed and admin invites only make admins, so the only way to a learner account is
`db/ops/create-test-learner.sql`. It creates exactly one adult learner (`is_minor = false`) for a Clerk user
that already exists, with a `TEST Learner` profile and one audit event (`accounts.create_test_learner`, by the
Owner). It refuses the Owner (by Clerk id or email), any existing account (it never converts an admin), an email
with an admin invite, and the untouched template. One transaction: a refusal changes nothing.

1. Clerk dashboard → **Users** → **Create user**: an email you control, not the Owner's and not starting with
   `ascentra-e2e-` or `ascentra-smoke-` (the test suites delete those), and a password.
2. Sign in on the site as that user. If Clerk asks to set up two-step verification, do it; otherwise open
   `/account` → Sign-in methods → **Security** → add an **Authenticator app**. (A password without a second
   factor is refused.) The site says the account isn't open yet: that's expected.
3. Clerk dashboard → that user → copy the **User ID** (`user_…`).
4. Supabase SQL Editor → paste `db/ops/create-test-learner.sql`, set `clerk_user_id`, `email` and `reason` at the
   top → **Run**. The last result row shows the new account (`role = learner`, `is_minor = false`) and its audit event.
5. Reload the site: "Signed in as TEST Learner (Learner)". The first page registers this browser as a trusted device.

## Applying B1 to Supabase (F6 is already applied)

Apply it **before** merging the B1 code: the B1 code reads the new tables and columns.

1. SQL Editor → **New query** → paste the whole of `db/apply/B1.sql` → **Run**. Expect "Success. No rows returned".
   If the editor warns about a destructive operation, that's `drop constraint subscriptions_status_check`, which
   the same file replaces at once with Stripe's statuses. `subscriptions` is empty, so nothing is deleted.
2. **New query** → paste `db/verify.sql` → **Run**. The first row must read
   `OK: all 45 tables … B1 billing is in place`.

## Applying F6 to Supabase (F5 is already applied)

Apply it **before** merging the F6 code: the F6 code reads the new columns on every API request, and
the F5 code that is live now ignores them.

1. SQL Editor → **New query** → paste the whole of `db/apply/F6.sql` → **Run**. Expect "Success. No rows returned".
   If the editor warns about a destructive operation, that's `drop constraint session_events_event_type_check`,
   which the same file replaces at once with a wider one. Nothing is deleted.
2. **New query** → paste `db/verify.sql` → **Run**. The first row must read
   `OK: all 43 tables … F6 devices, sessions and safeguards are in place`.
3. Optional: `select * from public.audit_verify_chain();` should still return `ok = true`.

`trusted_devices` starts empty: each browser registers on its first signed-in page after the deploy.

Break-glass only (the Owner has no working trusted device and can't pass a second-factor check):
`update public.trusted_devices set trust_state = 'revoked', revoked_at = now(), revoked_reason = 'removed'
 where account_id = (select id from public.accounts where role = 'owner') and trust_state = 'trusted';`
frees every Owner slot; the next sign-in registers a device again.

## Applying F3 to Supabase (0001 is already applied)

1. Supabase Dashboard → your project → **SQL Editor** → **New query**.
2. Paste the whole of `db/apply/F3.sql` and click **Run**. If the editor warns about a potentially
   destructive operation, that's the `drop constraint accounts_role_check`, which the same file
   immediately replaces with a wider one. Confirm and run.
   Expected: "Success. No rows returned". The Owner row and profile are kept.
3. **New query** → paste `db/verify.sql` → **Run**. The first row must read
   `OK: all 39 tables exist with row-level security on; audit_events and consent_records are insert-only`.

If step 2 fails, nothing was changed (it runs in one transaction); send me the error. Running it a
second time stops with "migration … is already applied. Nothing was changed."

Supabase's Security Advisor will list most tables as "RLS enabled, no policy". That is deliberate:
those tables are deny-all until their phase adds policies.

## Local development

```bash
# any local Postgres works; `supabase start` gives one at 127.0.0.1:54322
psql "$LOCAL_URL" -f db/test/supabase-shim.sql      # plain Postgres only, not `supabase start`
for f in db/migrations/*.sql; do psql "$LOCAL_URL" -v ON_ERROR_STOP=1 -f "$f"; done
SEED_DATABASE_URL="$LOCAL_URL" npm run db:seed        # refuses anything that isn't local
TEST_DATABASE_URL="$LOCAL_URL" npm run test:db        # creates and drops its own databases
```

## Direct access with a Clerk token

The `accounts` and `profiles` policies let a signed-in person read their own row if Supabase accepts
their Clerk session token (Supabase → Authentication → Third-party auth → Clerk). That isn't set up
and nothing needs it yet: without it, a direct call is anonymous and every table refuses it.
