security is on for every table and denies by default.

## A test learner by hand (Owner only; from B2 on, sign-up makes learners)

Sign-up is closed and admin invites only make admins, so the only way to a learner account is
`db/ops/create-test-learner.sql`. It creates exactly one adult learner (`is_minor = false`) for a Clerk user
that already exists, with a `TEST Learner` profile and one audit event (`accounts.create_test_learner`, by the
Owner). It refuses the Owner (by Clerk id or email), any existing account (it never converts an admin), an email
with an admin invite, and the untouched template. One transaction: a refusal changes nothing.

1. Clerk dashboard → **Users** → **Create user**: an email you control, not the Owner's and not starting with
   `ascentra-e2e-` or `ascentra-smoke-` (the test suites delete those), and a password.
2. Sign in on the site as that user. If Clerk asks to set up two-step verification, do it; otherwise open
   `/account` → Sign-in methods → **Security** → add an **Authenticator app**. (A password without a second
   factor is refused.) The site says the account isn't open yet: that's expected.
3. Clerk dashboard → that user → copy the **User ID** (`user_…`).
4. Supabase SQL Editor → paste `db/ops/create-test-learner.sql`, set `clerk_user_id`, `email` and `reason` at the
   top → **Run**. The last result row shows the new account (`role = learner`, `is_minor = false`) and its audit event.
5. Reload the site: "Signed in as TEST Learner (Learner)". The first page registers this browser as a trusted device.

Break-glass only (the Owner has no working trusted device and can't pass a second-factor check):
`update public.trusted_devices set trust_state = 'revoked', revoked_at = now(), revoked_reason = 'removed'

frees every Owner slot; the next sign-in registers a device again.

If step 2 fails, nothing was changed (it runs in one transaction); send me the error. Running it a
second time stops with "migration … is already applied. Nothing was changed."

Supabase's Security Advisor will list most tables as "RLS enabled, no policy". That is deliberate:
those tables are deny-all until their phase adds policies.

## Local development

```bash
# any local Postgres works; `supabase start` gives one at 127.0.0.1:54322
psql "$LOCAL_URL" -f db/test/supabase-shim.sql      # plain Postgres only, not `supabase start`
for f in db/migrations/*.sql; do psql "$LOCAL_URL" -v ON_ERROR_STOP=1 -f "$f"; done
SEED_DATABASE_URL="$LOCAL_URL" npm run db:seed        # refuses anything that isn't local
TEST_DATABASE_URL="$LOCAL_URL" npm run test:db        # creates and drops its own databases
```

## Direct access with a Clerk token

The `accounts` and `profiles` policies let a signed-in person read their own row if Supabase accepts
their Clerk session token (Supabase → Authentication → Third-party auth → Clerk). That isn't set up
and nothing needs it yet: without it, a direct call is anonymous and every table refuses it.
